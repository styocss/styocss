feat/122-watchable-icon-collections adds a generic `configDependencyAdded` sync hook in core (`packages/core/src/plugin.ts`), dedupe + notification in `Engine.addConfigDependency` (`packages/core/src/engine.ts`), wiring through `ctx.hooks.dependencyAdded` in integration (`packages/integration/src/ctx.ts`), a `registerLateDependency`/`pendingWatchFiles` bridge into the active bundler watcher in unplugin (`packages/unplugin/src/index.ts`), and a branded `WatchableIconCollection` descriptor (`packages/plugin-icons/src/watchable.ts`) plus a `fileSystemIconCollection` node helper (`packages/plugin-icons/src/node.ts`).

Reviewed clean — all suite counts verified by actually running each package after rebuilding upstream dist (core build → integration build → run core/integration/unplugin/plugin-icons tests): core 150/150 (98.81/96.59/98.88/98.97), integration 331/331 (98.16/95.81/97.32/98.33), unplugin 64/64 (99.27/98.12/100/99.25), plugin-icons 30/30 (99.27/96.15/100/99.25). Typecheck clean on all four packages.

Issue's 13-item required-test list: 13/13 have a mapped test (core `plugin.test.ts` dedupe/throw tests; integration `ctx.test.ts` wiring test; unplugin `index.vite-latedeps.test.ts` for items 8/9 — deliberately generic/not-icons-specific per the issue's explicit design constraint; `watchable.test.ts`'s 10 tests for the rest). The brand-vs-duck-typing test (`isWatchableIconCollection({ dependencies: SVG, source: SVG })` → false) is a genuine regression test: it would incorrectly return `true` under a naive `'dependencies' in value` check, which is exactly the rejected approach the issue calls out.

Non-blocking residuals (reported to owner, none required a change):
1. `packages/unplugin/src/index.ts`'s `pendingWatchFiles` → `this.addWatchFile(path)` flush (the finally-block branch guarded by `meta.framework !== 'esbuild'`) is only ever exercised through the real-vite integration test in `index.vite-latedeps.test.ts` — no webpack/rspack-specific test drives it. Low risk because the guard has no framework-specific branching beyond excluding esbuild (same code runs for vite/webpack/rspack alike), and coverage tool reports the lines/branches as hit, but a webpack/rspack regression here would go undetected by a dedicated test.
2. `packages/integration/src/ctx.test.ts`'s new test (`forwards dependencies registered during transforms to the dependencyAdded hook`) calls `ctx.engine.addConfigDependency(...)` *after* `await ctx.transform(...)` resolves, not from inside a plugin hook during the transform itself — so despite the comment/describe title ("transform-time", "discovered mid-run … during a module transform"), it doesn't actually prove reachability from inside the transform call stack, only that the `dependencyAdded` wiring exists at all (still fail-without-fix for the wiring itself).
3. Issue items 9 (edit → refreshed CSS) and 10 (delete-then-recreate) are covered by reasonable proxies rather than literally end-to-end: `vite-latedeps.test.ts` asserts a `full-reload` signal was sent on edit, not that regenerated CSS content changed; `watchable.test.ts`'s delete/recreate test uses two independent engines (consistent with #116's "fresh engine per re-derivation" model) rather than one running dev-server watch cycle.
4. Minor style nit: `index.vite-latedeps.test.ts` smuggles the engine instance into its test plugin via `(globalThis as any).__pikaTestEngine` instead of a local closure variable — works today (tests run sequentially, no `.concurrent`), but is an unnecessary global side-channel.
5. `cloneEngineConfig` preserving the `WATCHABLE_ICON_COLLECTION` symbol brand across the clone has no *icons-specific* direct unit test (only implicit, via real `createEngine()` + `isWatchableIconCollection` end-to-end behavior in `watchable.test.ts`) — but this is adequately backstopped by the pre-existing generic `config-clone.test.ts` test `'preserves opaque class-instance identity'`, which already pins the exact by-reference-if-prototype-isn't-Object.prototype mechanism the descriptor relies on.

**Why:** keeps the "does the regression test actually discriminate the bug" bar (established in [[issue_118_host_project_root]], [[issue_117_config_immutability]]) applied to a feature that spans all four packages in the core→integration→unplugin dependency chain at once — worth re-checking the same seams (transform-time vs. after-transform call-site, icons-specific vs. generic bundler-watcher plumbing) if a follow-up issue touches this code again.
**How to apply:** for any future change to `configDependencyAdded`/`registerLateDependency`/watchable-collection code, verify (a) upstream dist was rebuilt before trusting downstream green runs, (b) a claimed "mid-transform" test genuinely calls the dependency-adding code from inside the transform's plugin-hook execution rather than sequentially after it resolves, and (c) any non-vite bundler branch in unplugin's watcher bridge gets at least one dedicated assertion, not just incidental coverage from the vite path.
